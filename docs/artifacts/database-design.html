Database Design

Source of truth for the schema of «همکار فنی». PostgreSQL 16 + Redis 7. The agent/ service (FastAPI + Claude Agent SDK) and the arq worker share one database through SQLAlchemy 2; Alembic (in agent/migrations/) owns every migration. No other service writes to the database.

Conventions:

  • IDs = uuid v7 everywhere, with two exceptions (audit_log, check_result use bigint generated always as identity). Why v7: ids appear in URLs, SSE events and signed approval tokens, so they must not be guessable or enumerable (rules out bare bigint there); v7 is time-ordered, so btree inserts stay append-like and order by id ≈ order by created_at (rules out v4); the app can mint the id before insert, which the approval signer needs (it signs the approval id before the row commits). The two exceptions are append-only, high-row-count, never addressed by URL, and audit_log needs a strict total order for its hash chain. PG16 has no native uuidv7(), so migration 0001 adds uuid_generate_v7() (below) as the column default; the app uses uuid_utils.uuid7(). When we move to PG18, swap the function for uuidv7().
  • Times: timestamptz, stored UTC, rendered Jalali in the UI («۳ آبان ۱۴۰۵، ۱۲:۴۰»).
  • Money: bigint rial, suffix _rial. The UI divides by 10 and shows toman. Liara prices are copied with their source ("source":"liara:list_plans") — never estimated.
  • Persian text columns end in _fa; stored as written.
  • user is a reserved word in PostgreSQL: SQL must write "user". SQLAlchemy quotes it for us.
  • Enums are PostgreSQL enum types for closed sets (statuses, kinds). Tool names are text with a check constraint, because the list grows with the tool registry. Adding an enum value is ALTER TYPE … ADD VALUE in its own Alembic migration (it cannot be used in the same transaction).
  • JSONB only for payloads whose shape belongs to one feature (analysis, preview, evidence). Every JSONB column has a documented shape below and a Pydantic model in agent/app/schemas/.
  • Secrets (Liara token, env var values) live only as AES-GCM ciphertext. They never enter a JSONB column, a log line, the LLM context, or an SSE event.
-- 0001: extensions + uuid v7 (version bits 0111 set on a v4 base; 48-bit unix-ms prefix)
create extension if not exists pgcrypto;
create extension if not exists citext;
create function uuid_generate_v7() returns uuid language sql volatile as $$
  select encode(set_bit(set_bit(overlay(uuid_send(gen_random_uuid())
    placing substring(int8send(floor(extract(epoch from clock_timestamp()) * 1000)::bigint) from 3)
    from 1 for 6), 52, 1), 53, 1), 'hex')::uuid;
$$;

alter table tool_call add constraint tool_call_risk_matches_name check (
  case
    when name in ('analyze_repo','list_plans','get_balance','get_app_status','get_logs','get_metrics',
                  'list_releases','get_env_keys','check_dns','http_probe') then risk_class = 'read'
    when name in ('create_app','create_database','set_env','deploy_release','restart_app','resize_plan',
                  'rollback_release','add_domain','apply_code_fix','merge_and_deploy') then risk_class = 'sensitive'

    else false

  check (risk_class <> 'human_only' or status = 'limitation');

create function tool_call_gate() returns trigger language plpgsql as $$
begin
  if new.risk_class = 'sensitive' and new.status = 'running' and old.status <> 'running' then
    perform 1 from approval a
     where a.tool_call_id = new.id and a.status = 'approved' and a.args_hash = new.args_hash;
    if not found then
      raise exception 'sensitive tool_call % has no approved approval', new.id using errcode = 'P0001';
    end if;
  end if;
  return new;
end $$;

Secrets handling

Liara token (liara_connection.token_ciphertext):

  1. User pastes the token into a form that posts straight to POST /connections/liara (never into chat).
  2. Agent calls Liara /me with it; on 200, encrypts with AES-256-GCM: random 12-byte nonce, AAD = "liara_connection:{id}:{user_id}" (a ciphertext copied to another row fails to decrypt), key = HAMKAR_TOKEN_KEYS[HAMKAR_TOKEN_KEY_VERSION]. Stores nonce‖ciphertext‖tag, key_version, token_last4.
  3. HAMKAR_TOKEN_KEYS is an env var, JSON {"1":"<base64 32 bytes>","2":"…"}; it is never in the database, the repo, or a Docker image layer.
  4. Decryption happens only inside LiaraClient in the tool executor (agent tool-runner and worker), which builds the Authorization header itself. Tools receive a connection_id, never the token; the LLM sees tool *results* only, after the redactor.
  5. Never logged: the SQLAlchemy type EncryptedBytes has repr = "<encrypted>"; the structlog redaction processor drops keys matching token|authorization|secret|password|cookie and scrubs any string equal to a decrypted token; httpx request logging is off for the Liara client; Postgres runs with log_parameter_max_length = 0 and log_statement = 'ddl'.
  6. Rotation: add key "3", set HAMKAR_TOKEN_KEY_VERSION=3, deploy; the arq job rotate_token_keys re-encrypts rows where key_version < 3 in batches; when the count is 0, remove key "2" from env. key_version makes the mixed state safe.
  7. Revoke: status revoked, revoked_at = now(), token_ciphertext = '\x'; audit connection.revoked.

Env var values (set_env) follow the same path in tool_call.secret_args_ciphertext and are wiped after use. DATABASE_URL from create_database goes worker → ciphertext → set_env without passing through the agent's context. Previews show keys and a masked tail only.

Approvals: APPROVAL_SECRET (env, 32 bytes) signs approvals; rotating it simply invalidates pending approvals (max 10 minutes of loss).

Database roles: hamkar_migrator owns the schema (Alembic only); hamkar_app has DML on all tables except update/delete on audit_log; hamkar_readonly (students, evals, debugging) has select everywhere except liara_connection.token_ciphertext and tool_call.secret_args_ciphertext.

select * from (

    from incident i where i.id = :incident_id
  union all
  select e.captured_at, 'evidence.' || e.kind, e.id, e.summary_fa,
         jsonb_build_object('source', e.source, 'window', jsonb_build_array(e.window_start, e.window_end))
    from evidence e where e.incident_id = :incident_id
  union all
  select h.created_at, 'hypothesis', h.id, h.title_fa,
         jsonb_build_object('rank', h.rank, 'confidence', h.confidence, 'status', h.status)
    from hypothesis h where h.incident_id = :incident_id
  union all
  select a.created_at, 'approval.requested', a.id, a.preview->>'title_fa',
         jsonb_build_object('tool', a.preview->>'tool', 'delta_monthly_rial', a.preview#>'{cost,delta_monthly_rial}')
    from incident_action ia join approval a on a.tool_call_id = ia.tool_call_id
   where ia.incident_id = :incident_id
  union all
  select a.decided_at, 'approval.' || a.decision, a.id, a.preview->>'title_fa', null
    from incident_action ia join approval a on a.tool_call_id = ia.tool_call_id
   where ia.incident_id = :incident_id and a.decided_at is not null
  union all
  select tc.finished_at, 'action.' || tc.name, ia.id, null,
         jsonb_build_object('kind', ia.kind, 'status', tc.status, 'duration_ms', tc.duration_ms)
    from incident_action ia join tool_call tc on tc.id = ia.tool_call_id
   where ia.incident_id = :incident_id and tc.finished_at is not null
  union all
  select cf.created_at, 'code_fix.' || cf.status, cf.id, cf.branch_name,
         jsonb_build_object('pr_url', cf.pr_url, 'diff_stats', cf.diff_stats)
    from code_fix cf where cf.incident_id = :incident_id
  union all
  select v.verified_at, 'verification', v.id, v.method,
         jsonb_build_object('metric', v.metric, 'unit', v.unit, 'before', v.before_value,
                            'after', v.after_value, 'threshold', v.threshold, 'passed', v.passed)
    from verification v where v.incident_id = :incident_id
  union all
  select i.resolved_at, 'incident.resolved', i.id, h.title_fa, null
    from incident i left join hypothesis h on h.id = i.root_cause_hypothesis_id
   where i.id = :incident_id and i.resolved_at is not null
) t
order by at, kind;
